## Findings

### F4-1 | should fix | Three tasks in one commit
One commit (debc5a7) does T01, T02 and T03 (about 860 lines). CLAUDE.md step 4 and checklist 0.2 want one task per run, one commit and one tick set per task, so that a revert or a review can take one task at a time. Authorised ahead of gate 3 is not the same as authorised to bundle. Fix: from T04 on, one task per commit.

### F4-2 | should fix | Price tables are readable by any session of the club, including a guest
The `price_group`, `court_price_rule`, `coach_tier`, `coach_tier_price` and `add_on` read policies are `for select to booq_app, booq_worker using (true)`, behind only the restrictive tenant policy. The F02 guest context runs as `booq_app` with roles `['guest']` and a club id (F02 design 6.1), so at the database level a guest can read every row of these tables for any club in the context, including a Draft or Testing club. D102 says a non-live club shows nothing but a minimal sign-in config, and D103 says a guest reads named public columns or routes only. The route layer is meant to stop a guest reaching a non-live club, but the database policy is the second line the design promises. Prices are not secret once the club is live; the issue is the rule, not the data. Fix: restrict the read policy to `app.user_id() is not null` or to a club that is live or paused (for guests), and add the test "a guest cannot select from a Draft club's price tables" to T05's blind suite. Low risk today because nothing serves these tables to a guest yet.

### F4-3 | note | `promo_redemption.customer_id` is nullable and has no foreign key
`birthday_entitlement_use.customer_id` is `not null` with a composite foreign key to `app_user`, but the redemption's is a bare nullable uuid. The per-customer cap and first-time-only rules (PROMO-01-AC5, AC6) count by customer, and a null customer cannot be counted. Either `not null` with the same foreign key, or state when a null customer is allowed (a staff walk-in with no player?). **QUESTION** for the Architect.

### F4-4 | note | Re-counting a restored use on the same order
`promo_redemption` is unique per order and a restored row stays. A late payment that reclaims the same order (PAY-03-AC7; spec-consistency F03-2) must therefore flip the existing row back to `counted`, because a second row for the order is refused. The check constraint allows that, but no test covers it and T04's list does not mention it. Add to T04: re-count on reclaim updates the same row under the promo lock, and a capped code that is now full refuses it.

### F4-5 | note | Peak and off-peak can be stored
`court_price_rule.peak` accepts `peak` and `off_peak`, and the lookup rejects them (design A-4, D111). If the owner saves only a peak rule through T13, every hour for that group has no rule and is refused. T13 should reject peak values at save, with a test.

### F4-6 | note | `generated/schema.ts` is in the commit
The build plan says generated types are regenerated by CI and never merged by hand. The commit adds 143 lines. If a script produced them, say which in the commit message; the CI "generated types are current" check is the guard, and it is still advisory until `CI_STRICT=true` (W0-4).

### F4-7 | note | Casts in check constraints
`price_group_rule_shape` casts `rule ->> 'min_age'` to integer, so a non-numeric age raises a cast error (22P02) rather than a check violation. Harmless; route validation (T13) should catch it first.

### F4-8 | note | Who may read prices and codes
Every club person (player, coach, front desk, accountant, owner) reads all five price tables; front desk and accountant read promo codes and partners. D115 limits the Accountant to business and tax settings; prices and codes are not settings, and the hand-off lets the Accountant read reports and receipts, not codes. Confirm with the Orchestrator that accountant read access to codes and partners is intended. Same for a coach reading other tiers' prices (a player sees them anyway).

### F4-9 | note | `scope jsonb` and `applies_to`
`order_line.scope` has no stated shape, and `promo_code.applies_to` allows `solo_class` although partner codes on a solo class are parked (canvas gap A4). The rule sits in the engine (T08, a test is planned); the database does not guard it. Record the `scope` shape in the design.
